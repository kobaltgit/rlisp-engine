# Регламент разработки rlisp-engine (AI_AGENTS.md)

Данный регламент является обязательным руководством для всех AI-агентов и разработчиков, работающих с кодовой базой **rlisp-engine**.

---

## 1. Запрет на раздутие файлов (Anti-Monolith & File Size Guard)
* **ЖЕЛЕЗНЫЙ ЛИМИТ:** Ни один файл исходного кода в `src/` не должен превышать **800 строк**.
* **ЦЕЛЕВОЙ ОРИЕНТИР:** Рекомендуемый комфортный размер модуля — **от 150 до 500 строк**.
* **ЗАПРЕЩЕНО:**
  - Дописывать новый функционал в монолитные файлы, превышающие 800 строк;
  - Создавать новые файлы размером более 800 строк;
  - Сливать разные зоны ответственности в один файл «для удобства».
* **ПРАВИЛО ДЕКОМПОЗИЦИИ:** Если модуль приближается к 800 строкам, агент обязан выделить из него подмодули в подпапке `src/<module>/`:
  - `mod.rs` — лаконичный фасад с реэкспортом через `pub use`;
  - `types.rs` — структуры данных и перечисления;
  - `shading.rs` / `raster.rs` / `primitives.rs` / `lisp.rs` — профильная логика;
  - `tests.rs` — модульные тесты.
* **АВТОМАТИЧЕСКИЙ КОНТРОЛЬ:**
  - Проект содержит автоматический тест `tests/file_size_lint_test.rs`, проверяющий отсутствие файлов > 800 строк при каждом запуске `cargo test`.
  - Монолиты из списка `PENDING_REFACTORING` удаляются из исключений сразу по завершении их модульной декомпозиции.

---

## 2. Ограничение ресурсов при компиляции (Resource Guard)
* **СТРОГО ЗАПРЕЩЕНО** запускать команды компиляции и тестирования без явного флага ограничения потоков:
  ```powershell
  cargo test --workspace -j 1
  cargo check -j 1
  cargo build --release -j 1
  ```
* Всегда использовать `-j 1` во избежание перегрузки процессора и оперативной памяти рабочей машины.

---

## 3. Философия Zero-Core Hardcoding (Lisp-First Architecture)
* **Rust — это исключительно быстрый HAL / GPU / T&L конвейер.**
* Вся игровая логика, сущности, физические правила, анимации, HUD, управление и демки пишутся **ИСКЛЮЧИТЕЛЬНО на Lisp** в папке `assets/lisp/` (например, `game3d.lisp`, `island.lisp`, `oasis.lisp`, `tetris.lisp`).
* **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО** вшивать в ядро Rust специфичные проверки под конкретные игры (например, `if game == "tetris"`, хардкод цветов блоков, специфичные ветвления в матчингах под ID сцен).
* Ядро должно оставаться нейтральным, универсальным исполняемым рантаймом.

---

## 4. Критерий завершения задач (Definition of Done — 100% Тесты)
Ни один шаг, задача или исправление дефекта не считаются завершенными без:
1. **100% успешного прогона тестов воркспейса:**
   ```powershell
   cargo test --workspace -j 1
   ```
   Команда обязана завершиться с кодом возврата `0`, нулевым числом упавших тестов и прохождением линтера размера файлов `file_size_lint_test`.
2. **Отсутствия предупреждений компилятора (`warnings`).**
3. **Сохранения обратной совместимости:** внешние модули должны продолжать видеть прежние публичные контракты без необходимости рефакторинга вызовов.

---

## 5. Работа со сложными задачами (Микропланы и контекст)
* При масштабных рефакторингах (декомпозиция файлов от 1000 строк) агенты **обязаны** делить задачу на серию самодостаточных микропланов в артефактах (например, `microplan_r3_01_*.md`, `microplan_r3_02_*.md`).
* Каждый микроплан выполняется в отдельной итерации с промежуточной верификацией через `cargo check -j 1`.
* Это исключает переполнение контекстного окна и гарантирует устойчивость процесса.
