# Архитектура

«Игровой движок как Lisp-машина: Rust только как HAL, всё остальное — DSL».
Каждый слой знает только о слое под ним; Lisp-уровень не знает о выборе
рендер-бэкенда.

## Четыре слоя

```
┌──────────────────────────────────────────────────────────────────────┐
│  УРОВЕНЬ 4: Игровые DSL (жанровые)                                   │
│  (defgame survival …) (defenemy grunt …)       «ORBITAL» (game3d.lisp)│
├──────────────────────────────────────────────────────────────────────┤
│  УРОВЕНЬ 3: Системные DSL — всё на Lisp (assets/lisp/)               │
│  graphics │ input │ ecs │ physics │ render3d │ textures │ editor     │
├──────────────────────────────────────────────────────────────────────┤
│  УРОВЕНЬ 2: Lisp-интерпретатор + SAL (src/interp.rs, src/simd.rs)    │
│  Reader │ Evaluator (TCO) │ defmacro/quasiquote │ F32Vec │ GC      │
├──────────────────────────────────────────────────────────────────────┤
│  УРОВЕНЬ 1: Rust HAL (src/hal.rs, render3d.rs, gpu.rs, png.rs,       │
│  editor.rs, mcp.rs, json.rs) — окно/растр │ бэкенды рендера:         │
│  software │ wgpu (offscreen+readback) │ 3D-«GPU»: T&L+z-буфер+батчи  │
│  │ ввод │ память │ время │ PNG-кодек │ HTTP │ MCP                    │
└──────────────────────────────────────────────────────────────────────┘
```

## Рендер-бэкенды за фасадом HAL (этап 1)

```
 Lisp: (gpu-clear) (gpu-fill-rect) (gpu-blit) (gpu-blit-tex) (gpu-present)
                     │
                     ▼
   Hal::clear_all / fill_rect / blit / blit_tex / flush_gpu   ← фасад
                     │
        ┌────────────┴─────────────┐
        ▼                          ▼
  Backend::Software          Backend::Wgpu(Box<dyn GpuBackend>)
  программный растр:         (фича `wgpu`, wgpu 0.20):
  команды пишут прямо        команды → offscreen-текстура RGBA8
  в Hal::fb (как в           (alpha = маска покрытия), при flush:
  v0.1–v0.3)                 copy-to-buffer → map-read → композит
                             в Hal::fb по альфе-покрытию
```

Контракт `GpuBackend`: `clear / fill_rect / blit / blit_tex / resize /
tex_upload / tex_free / flush(fb, readback) -> (submit_ns, readback_ns)`.
`Hal::flush_gpu()` — единственная точка, где GPU-слой попадает в fb; она
вызывается из `gpu-present`, `gpu-screenshot`, перед каждой 3D-командой
(порядок художника = как у программного растра) и перед публикацией кадра
веб-редактору.

### Композит по альфе-покрытию

Кадр wgpu-бэкенда живёт в offscreen-текстуре, где alpha — маска «GPU
рисовал сюда» (clear заливает alpha=1 весь кадр, квады пишут alpha=1,
не покрытые пиксели остаются alpha=0). Readback копирует текстуру в
выровненный по 256 байт буфер, `composite_readback()` переносит в fb только
покрытые пиксели — под ними может быть результат программного 3D-конвейера.
Так PNG/ASCII/редактор читают один и тот же fb при любом бэкенде.

### Честно о покрытии этапа 1

- wgpu закрывает **2D-растр** (clear / fill-rect / blit / blit-tex /
  present);
- 3D-конвейер (`render3d.rs`: T&L, z-буфер, батчи) остаётся **программным**;
  перенос батчей на GPU — этап 5 роадмапа;
- критерий «`--wgpu` кратно быстрее» требует GPU-железа — см.
  `docs/benchmark.md`.

## Менеджер GPU-ресурсов

`GpuResources` (без устройства — работает и на software-пути):

- `register/free/live/bytes/generation` — книга хэндлов, зеркалит реестр
  `hal.tex` (id = индекс+1);
- перезагрузка живого id замещает старое поколение (free+create) — счётчики
  честные: `tex_created − tex_freed == живые хэндлы`;
- hot-reload: `Hal::invalidate_textures_except(keep)` освобождает всё,
  кроме id, которые встречаются среди persistent-значений
  (`gpu::collect_int_refs` обходит таблицы/списки/векторы). Тест-критерий
  этапа: 100 create/reload циклов без роста памяти;
- на wgpu-стороне рядом живёт `HashMap<id, wgpu::Texture>` — удаляется
  вместе со слотом (утечек нет: drop текстуры возвращает память GPU).

## Tracing-GC (этап 2)

До этапа 2 владение было на `Rc` — цикл «замыкание ↔ окружение» не
освобождался никогда. Теперь пары, замыкания и окружения живут в арене
`src/gc.rs`; в `Value` лежит хендл `Gc` (индекс слота + поколение):

```
 Value::Cons(Gc)──▶ слот кучи: Pair(RefCell<(Value, Value)>)
 Value::Lambda(Gc)▶ слот кучи: Lambda{ params, rest, body, env: Gc, is_macro }
 глобальное окружение ─▶ слот кучи: Env{ vars, parent: Option<Gc> }
```

- **Корни**: глобальное окружение (ячейка `GlobalCell`), RAII pin-наборы
  (`gc::pin` — результаты REPL, persistent-значения при hot reload),
  дополнительные значения от драйвера (очередь ввода `Hal::queue`).
- **Mark**: обход от корней; Rc-контейнеры (`Vector`/`F32Vec`/`Table`/строки)
  для маркировки прозрачны — заходим внутрь, чтобы пары/замыкания внутри
  живого контейнера не были собраны; сами контейнеры освобождаются по Rc
  (циклов через них в куче нет — у `Lambda` нет Rc-полей). Циклы гасятся
  флагом пометки и seen-наборами адресов.
- **Sweep**: непомеченные слоты освобождаются, слот переиспользуется через
  free-list; поколение слота растёт — обращение по висячему хендлу даёт
  панику с внятным сообщением, а не порчу памяти.
- **Когда собираем — только на границах форм** (стек вычислителя пуст):
  значения в локальных переменных рекурсивного `eval` недоступны обходу
  корней. Глубина стека eval считается guard'ом: `maybe_collect` при
  активном eval честно откладывает сборку (ставит флаг), прямой
  `collect()` во время eval — паника-детектор. `(gc)` и авто-порог
  (макс(8192, 2×живых)) срабатывают на следующей границе.
- **Примитивы**: `(gc)` — попросить сборку; `(gc-stats)` — таблица
  collections/allocs/freed/live/peak-live/threshold/requested.

Что НЕ трассируется (честно): `Vector`/`F32Vec`/`Table`/`Str` остаются
Rc-значениями; Rc-циклы через сами контейнеры (таблица в себе) не
собираются. Нативы не прячут GC-хендлы в захватах (проверено: они держат
только `GlobalCell`/`CoreCtx`/`Hal` — сами корни).

## Потоки (этап 2): MCP в фоне, интерпретатор однопоточный

MCP (JSON-RPC 2.0, stdio) обслуживают фоновые потоки; игровая нить —
единственный владелец интерпретатора. Потоки общаются ТОЛЬКО каналами:

```
 поток-reader (stdin)                 игровая нить (владелец interp)     поток-writer (stdout)
 ────────────────────                 ──────────────────────────────     ─────────────────────
 строка → JSON → McpRequest  ─mpsc▶   mcp_engine_loop:                   ◀mpsc─ строка ответа
 (parse-ошибка → ответ сразу)         между кадрами разбирает очередь,   println + flush
                                      инструменты применяет здесь же
```

- reader не касается интерпретатора: только разбор протокола в данные
  (`McpRequest` — owned, `Send`);
- игровая нить применяет инструменты между кадрами; при пустой очереди
  ждёт следующий запрос (`recv` — «пауза между кадрами»); EOF stdio
  закрывает канал и цикл завершается;
- writer — единственный писатель stdout, строки ответов не перемешиваются;
- Values и `Hal` никогда не покидают игровую нить, блокировок на
  состояниях нет — гонок по построению. `--mcp` поведение совместимо.
- Веб-редактор (`--serve`) устроен так же с v0.3: HTTP-нити отвечают из
  моста, Lisp исполняет только игровая нить (командная очередь).

## SIMD-токенизатор и JIT (этап 3)

### Пайплайн чтения: два пути, одна семантика

```
.lisp-файл ─┬─ parse_program_simd  (x86_64): byte-class скан SSE2 (src/simd.rs)
            │   next_hit(bytes,pos): 16 байт за раз, точные множества
            │   {WS = 09..0D,20} {DELIM = ()[] quote backtick comma semicolon dquote } через pcmpeqb+movemask,
            │   find_byte (memchr-стиль) для ;-комментариев и сканов в строках
            └─ parse_program_scalar (fallback + эталон): посимвольно,
                Vec<char> + is_whitespace + contains
                    ↓ одинаковый AST (сверка обязательна: тесты + --bench-parse)
                 Value::List/Sym/Int/Float/Str → eval
```

Юникод (комментарии и строки с кириллицей, U+00A0-пробелы) обрабатывается
скалярно только на байтах ≥ 0x80 — для 100% ASCII-источников скаляр не
выполняется. Старый путь остаётся эталоном: любое расхождение AST — ошибка
сборки, бенчмарк не продолжается.

### Пайплайн JIT: reader → IR → гарды → машинный код → деоптимизация

```
(lambda (x y) ...)                     Value::Lambda (GC-куча, src/gc.rs)
   ↓ try_call_lambda: кэш по (idx,gen), компиляция однажды
Compiler (src/jit.rs): Lisp → линейный IR
   стековая машина над f64: значение выражения в xmm0, let-слоты и левые
   операнды бинарных операций — на f64-стеке (rsp)
   поддержано: + - * / < = > <= >= (лист-позиции), if над сравнением,
   and/or над сравнением (короткое замыкание), let (≤8 связываний),
   литералы, параметры, begin
   НЕ поддержано (честная деоптимизация = compile → None): вызовы функций,
   рекурсия, строки/списки, quote, set!, макросы, if над «просто числом»
   (семантика ±0.0/NaN непереносима в comisd без искажений)
   ↓
emit.rs: IR → x86-64 байтовыми шаблонами (copy-and-patch, CPython-style)
   movsd/addsd/subsd/mulsd/divsd/comisd + setcc/cvtsi2sd (булевы 0.0/1.0),
   push/pop через sub rsp,8 + [rsp], константы — RIP-относительный пул,
   переходы — rel32-фиксапы (patch после эмиссии)
   гарды в коде: деление на ±0.0 → NaN-протокол runtime-деоптимизации
   ↓
mmap(RW) → копия кода → mprotect(R|X)  (W^X; прямые syscall через asm!)
   ↓
JitFn::call: unsafe fn(*const f64) -> f64, результат → Value::Float
   провал гарда арности/типов в call_jitted → None → интерпретатор
```

Деоптимизация трёх уровней, все прозрачные: (1) компиляционная — unknown
форма, JIT просто не строится; (2) входная — нечисловой аргумент или арность;
(3) runtime — деление на ноль (interp возвращает ошибку, а не inf). Ни один
путь не даёт «частично посчитанного» результата: либо JIT целиком, либо interp.

### Честно о покрытии этапа 3

Критерий eval/JIT ≥5× выполнен (49× на бенч-сцене вызова числовой лямбды —
это НЕ ускорение всей игры: ускоряется вызов маленькой числовой лямбды).
Критерий парсер ≥3× НЕ достигнут (1.07×; разбор — в roadmap.md и
benchmark.md): парсер аллокационно упирается, а не скан-ом. Свойственные
тесты (3000 seeded случайных выражений, interp vs JIT) — зелёные и остались
в наборе как регресс-щит.

## Zero-dependency по умолчанию

`[dependencies]` пуст; wgpu — `optional = true` за фичей `wgpu`. Cargo.lock
содержит и опциональный граф (optional-зависимости резолвятся всегда),
поэтому CI проверяет ноль зависимостей через `cargo tree -e normal
--prefix none` (в дефолтной сборке виден только корень), а не через grep
лока.
